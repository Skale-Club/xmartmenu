# Native AI access and usage persistence

The existing `OWNED_ADMIN_MENUS_ENABLED` selection now routes the AI access module's platform/tenant configuration reads, rejected-key warning update and usage-event insertion to explicit SQL adapters. All operations share the existing two-connection admin pool and bounded transactions. Source branches remain intact when the flag is off; native database failures never select Source.

Encrypted panel/tenant credentials retain the existing server-only decryption, environment-default policy, billing-mode selection, markup arithmetic and provider-key fallback rules. A missing configuration row retains existing defaults; an unavailable native read fails before any provider invocation. A rejected tenant key's warning is saved before the existing paid platform-key fallback. If that native update fails, the fallback is not executed. Provider requests never hold a database transaction open.

Usage insertion projects only the existing tenant/feature/model/key-source/billable/cost/markup/charge/generation/request fields. Invoice, billing-batch and settlement columns are untouched. The existing best-effort metering contract remains: if usage recording fails after a provider already returned, the failure is logged and the original response remains readable. This slice adds no retry, charge, duplicate-detection rule or claim of atomicity with an external provider. Invoice batching/Stripe settlement and panel configuration writes are separate remaining migration work.

Seven offline cases and five disposable PostgreSQL cases cover native selection/failure, encrypted-setting compatibility, tenant isolation, rejected-key fallback ordering, unchanged real-cost arithmetic, provider-response preservation, decimal persistence, null-tenant platform work and rollback. No real provider/Stripe call, key rotation, DDL, production data or flag change is performed. Message/audio/catalog migration still follows before a complete native chat rollout.
