# Native AI usage billing (prepared; rollout disabled)

The existing admin-menu flag selects native Bill now before constructing a Source client. False retains the existing Source function. Renewal invoice events use the same native coordinator; other SaaS/Connect events keep their single-transaction path. No provider call, production mutation, credential, role, flag or schema application is part of the tests or code publication.

The [OWNED-only SQL proposal](proposals/native-ai-billing-owned-only.sql) adds one RLS-protected request ledger. It is deliberately outside Supabase migrations and is not auto-applied. Its explicit runtime grants permit insert/read and state-column updates, while immutable request facts cannot be updated or deleted by runtime. Before actual apply, a separate reviewed candidate operation must preserve all47 existing business tables,95 migration rows, roles, data digests and the established connection budget, with an encrypted restoration-proven backup. Missing ledger/grants refuse rather than use Source.

Tenant deletion keeps its existing behavior: a nullable FK sets only the live tenant reference to NULL. The original tenant UUID remains in immutable body/hash facts, and confirmed history is retained. Every new financial attempt requires the current non-null exact tenant; orphaned requests cannot create/retry. If deletion happens after the external effect, state-only refusal records reconciliation_required without a success receipt or automatic compensation.

The short prepare transaction locks tenant before subscription/usage, claims only eligible billable usage through the cutoff and freezes the exact customer/invoice/amount/currency/description/metadata, usage membership hash and provider account/livemode/API version. Existing no-customer, no-usage and below-cent results remain no-charge outcomes. A legacy claimed batch without its immutable request is not reconstructed; it requires reconciliation. Batches above50000 rows refuse as a whole, without partial claims or a charge.

Tenant serialization uses FOR NO KEY UPDATE, as do tenant-plan and SaaS lifecycle reconciliation. This conflicts with other tenant writers/deletion while allowing the FK KEY SHARE locks required when a concurrent admin transaction inserts missing settings after reading the subscription. A concurrent PG fixture exercises that complete lock sequence rather than relying only on SQL text.

Before a create, a second transaction checks provider context, membership and the durable request, then records a CAS token with a30-second lease and the original first-attempt time. Only a committed claim permits network execution. Each provider account/mode read and create has a6-second timeout, zero SDK retries and pinned API version. No SQL connection stays held during network I/O; the existing admin pool stays capped at two.

A crashed/rolled-back finalization can resume with the identical saved request and idempotency key after the lease expires, within20 hours of the first durable attempt. A current SDK exception or returned-item mismatch marks reconciliation_required; it does not automatically issue another create. An expired attempt, account/mode/version mismatch, live lease, changed membership or uncertain commit refuses before a new financial call. If persisting a refusal itself fails, the request facts/lease remain durable and no success is returned. There is no automatic provider search or financial reconciliation in this slice.

Returned items must match customer/invoice (string or expanded ID), amount, currency, description, metadata and mode. Finalization rechecks the CAS token and exact usage facts, then commits the usage mark, confirmed item and invoice event receipt together. A local mark/receipt failure propagates without declaring success or releasing the batch. Duplicate renewal receipts skip provider calls. Distinct delivery snapshots retain the documented SaaS behavior; no ordering by timestamp is invented.

Offline gateways cover request options, exact-body reuse, no Source fallback, no-charge/duplicate outcomes, provider errors, mismatched returned facts and local finalization failures. Disposable PostgreSQL tests cover concurrent claims, crash recovery,20-hour refusal, tenant/context/lease/membership gates, legacy-batch refusal, no-charge semantics, invoice receipt atomicity, table constraints and actual state-only runtime grants. None calls Stripe. Fixtures do not prove actual candidate privileges/provider acceptance.

The new ledger's reviewed candidate apply, final Source write barrier and full business reconciliation, real provider configuration/acceptance and all remaining SQL/Auth consumers remain production gates. All flags stay off until those gates close. Stripe idempotency retention is bounded; this code never interprets an old/ambiguous remote outcome as permission to start a fresh charge ([official reference](https://docs.stripe.com/api/idempotent_requests)).
