# Native SaaS and Connect webhook contract

The existing signature verification remains before any SQL or side effect and uses the original raw body. Native order-payment dispatch remains separate. The admin-menu flag selects this repository before constructing Source clients; false retains the existing handler. No flags, credentials, provider resources, charges or production data are changed by preparation/tests.

| Event | Preserved native behavior |
| --- | --- |
| checkout.session.completed, kind=plan | Activate/update the supplied tenant subscription, optional plan/customer/subscription IDs, clear period-end cancellation; plan-activated CRM intent. |
| checkout.session.completed, addon=chat | Set paid addon active/since and optional customer ID. |
| customer.subscription.updated/deleted, kind=plan | Resolve old/new period shapes and price-to-plan/cycle, map live/trial/cancelled/past-due states, backfill subscription ID by tenant, reconcile the canonical service switches; churn/plan-direction CRM intent. |
| customer.subscription.updated/deleted, addon=chat | Keep active only for live/trialing; pending cancellation keeps access; deactivate the widget when no longer active. |
| invoice.payment_failed | Resolve the plan subscription from top/parent/line shapes, mark past-due and reconcile service switches; past-due CRM intent. |
| account.updated | Resolve the unique connected account; only charges_enabled changes active state, ignoring payout-only flaps; connect CRM/security intents. |
| invoice.created | Non-renewal/non-draft/unmatched invoices remain no-op receipts. Matched draft renewals are delegated by runtime to the native billing coordinator, which preserves no-charge outcomes and finalizes usage plus receipt atomically. The direct single-transaction repository refuses required billing rather than perform network I/O in a transaction. |
| Other non-payment events | No business change, durable receipt. Payment-intent types cannot be swallowed by this repository. |

The same event advisory-lock namespace as native Payments (190732) serializes duplicate IDs. A previous receipt with a conflicting non-null type refuses. Receipt plus metadata/reconciliation commit in one bounded transaction; receipt failure rolls everything back, without SQL retries. Tenant locks precede subscription/plan work, using the query-based helper from the tenant-plan slice. Ambiguous provider-to-tenant/plan mappings fail before mutation. Return only received/skipped publicly; enqueue the existing fail-open thin QStash intent after commit and never on a duplicate. No new durable outbox or guarantee of CRM delivery is introduced.

Current valid event shape/status/response behavior is retained. Distinct snapshot events still apply their supplied facts; no invented ordering by timestamp is added. The code handles subscription-before-checkout backfilling as before. [Stripe delivery guidance](https://docs.stripe.com/webhooks) documents duplicate and unordered delivery; [signature/recovery guidance](https://docs.stripe.com/events/manage-webhook-endpoints) requires original-body verification and persistent duplicate tracking.

The native [billing coordinator](xmartmenu-native-ai-billing.md) adds durable immutable request facts, bounded CAS/lease recovery and an OWNED-only ledger proposal. The Source biller is never called from this native path. Stripe v1 idempotency can expire and compares retry parameters, so replaying an ambiguous financial request blindly is insufficient ([official idempotency reference](https://docs.stripe.com/api/idempotent_requests)). Missing schema/grants, legacy unknown batches and uncertain/expired financial outcomes refuse without a Source fallback or false success receipt. Reviewed candidate DDL, Source fence/reconciliation and real provider acceptance remain required before rollout.

Ten offline cases (20 including existing payment routing checks) pass, covering real SDK signatures/raw bytes, dispatch and post-commit intents without provider/billing calls. Ten PostgreSQL cases cover event families, tenant/price/provider ambiguity, concurrency/replay/type conflict, both period/invoice shapes, canonical reconciliation, rollback and the invoice boundary. PostgreSQL fixtures are disposable projections and clean up before independent identity migrations. They do not prove live grants, delivery settings or provider acceptance.
