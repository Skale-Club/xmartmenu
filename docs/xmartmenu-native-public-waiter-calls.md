# Native public waiter-call creation

The public table-link endpoint selects native SQL through the existing `OWNED_ADMIN_MENUS_ENABLED` flag before constructing a source client or calling the source-backed plan helper. It shares the existing admin pool of two connections and transaction budget. Native request bodies are bounded by the existing public body reader. The legacy branch stays available while flags remain off.

The native writer checks an active restaurant by slug, the current active/trial plan's orders/payments features, master order switch and waiter/guest service switch, then the supplied active table under that exact tenant. It uses the shared pure capability/reason rules. Shared row locks hold the admitted restaurant/settings/subscription/plan during the operation; a lock on the stable table row serializes concurrent first calls without new DDL or a uniqueness assumption.

Only the newest non-done call with the same tenant/table/reason and creation within two hours is reused. A repeat returns the same ID and HTTP 200, reopens the call, clears prior acknowledgment and bumps last-called time. Creation returns 201, snapshots the trusted table name and lets existing database defaults supply ID/status/timestamps. Done, stale and different-reason calls remain distinct. Every change commits atomically; errors never switch to source writes or acknowledge a failed reopen.

Six offline cases and six disposable PostgreSQL cases cover native selection, plan/switch admission, immutable scope, concurrent first taps, repeats, acknowledgment clearing, stale/done separation and failed-write rollback. Fixtures are limited projections; they do not prove production grants or source realtime delivery. This slice changes only public creation/reopening. Staff acknowledgment, its existing `acknowledged_by -> auth.users` foreign key, staff reads/realtime and new native-user support remain separate required work before a full waiter rollout. No DDL, provider operation, role or live flag changes occur here.
