# Native customer identity and current phone evidence

This slice leaves all authentication, Google and database flags unchanged. It performs no live SQL, imports, provider writes, role changes or new DDL. The native branches require the existing independent orders/payments adapters; mismatched rollout flags fail closed.

`getOwnedCustomer` first uses the native principal/session/profile guard. A second, parameterized session-to-binding read checks the hashed opaque token, exact app UUID, expiry, version, disabled controls and provider provenance. A Google-only binding retains its app UUID with no phone assertion. A phone binding uses a fresh, bounded Google `users.get` lookup for that exact project/subject; the current E.164 account phone must agree with one phone-provider credential. Contacts, profile phone fields, emails, MFA metadata and old JWT phone claims grant nothing. The Google lookup uses the existing ADC/permission, an explicit response field mask, no-store, a 64 KiB body cap and an eight-second total deadline. No provider result is cached across requests.

Phone-only requests make an additional bounded metadata lookup after the normal provider revocation check. UUID-only payment authorization uses the native principal directly and incurs no extra phone lookup. An unavailable current lookup is an error; it does not downgrade to source Auth or anonymous ordering.

If an existing Google binding subsequently proves phone sign-in for the same provider subject, `bind` can promote its provider provenance to `phone`. This requires a fresh verified phone token, independently proved owned/source session ownership of the same app UUID, a locked existing binding, and a coherent current Google phone check inside the same PostgreSQL transaction. A changed number, revoked binding/provider, wrong UID or unapproved proof kind rolls back. The operation changes no role, app UUID, tenant or proof category and never writes to Google.

## Application paths

- Payment intents select native UUID authentication before any source SDK construction. Canonical staff role plus matching tenant, superadmin role or exact order customer UUID authorize a request. A customer with a tenant field does not inherit staff privileges. Pricing, Stripe intent handling and webhooks remain unchanged.
- Guest checkout preserves native UUID ownership even without a phone. Private-menu checkout additionally requires current phone evidence. Provider failures do not become anonymous orders.
- Private menu checks run for every request outside the shared catalog cache. A previous visitor's access or an old phone cannot expose cached private categories/products/options.
- `/[slug]/me` reads only that restaurant's orders owned by the verified app UUID. Google-only accounts can view their existing orders. Current verified phone evidence may claim anonymous rows using the original `link_orders_to_verified_phone` predicates: same tenant, no current owner and exact E.164; never a suffix or an old number. The claim and history read use one bounded transaction with current local account/profile controls. Claim failures roll back to a savepoint, retain existing UUID history and display an explicit incomplete-link message.
- Customer login uses server authority before constructing any legacy Auth SDK. Native sign-in/phone linking returns to a server-validated local customer destination; recovery checks take precedence. Native customer signout requires a confirmed native logout and creates no source Auth client.

## Verification and remaining gates

Offline tests cover Google-only UUIDs, current/changed/missing phone evidence, incoherent or duplicated provider records, exact subject selection, deadline/body bounds, revoked sessions, phone promotion rollback, private cache isolation and native orders/payments without source factories. Seven additional disposable PostgreSQL cases exercise promotion, payment role isolation, tenant/UUID/E.164 order claims, savepoint recovery and current local controls. Projection fixtures are not a complete production schema/grants or provider/UI acceptance proof.

Flags remain off pending native new-customer registration, onboarding, recovery/account management, provider-backed staff/admin management, waiter/backoffice consumers, custom-domain auth transport and remaining SQL/browser/Storage/MCP-OAuth surfaces. Existing phone-only source accounts without a password still need their independent old-session proof linked during the reviewed pilot or reviewed recovery; contacts cannot replace that proof. Final source reconciliation, enforced write barrier, rollback proof and real phone/Google acceptance remain mandatory before activation.

Primary references: [Google account fields](https://docs.cloud.google.com/identity-platform/docs/reference/rest/v1/UserInfo), [provider identity fields](https://docs.cloud.google.com/identity-platform/docs/reference/rest/v1/ProviderUserInfo), [system response field masks](https://docs.cloud.google.com/apis/docs/system-parameters). The stricter requirement that account phone and a unique phone credential agree is this application's admission rule, derived from those fields and the locally recorded binding provenance.
