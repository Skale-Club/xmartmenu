# Native registration and onboarding candidate

Code is gated off by default: `OWNED_REGISTRATION_ENABLED=true` additionally requires `OWNED_AUTH_ENABLED=true` and `GOOGLE_AUTH_ENABLED=true`. Onboarding additionally requires `OWNED_ONBOARDING_ENABLED=true`. No flag or production database was changed by this PR.

Explicit new-account operations `/api/identity/register-customer` and `register-business` reuse the identity browser challenge, same-origin checks, provider JWT verification, provider liveness and existing identity pool (max2). Creation inserts a generated UUID profile, app account, provider binding and hashed native session in a single transaction. Customer flow fixes role to customer. Business flow fixes role to store-admin, the canonical migration005 signup default, with no tenant. Clients cannot supply roles, tenants, memberships or IDs. Existing bound identities, disabled bindings, and matching phone contacts stop for independent linking/recovery; no contact ever grants ownership. Verified Google email is not used as an account lookup or owner proof. Email-only historical accounts must independently link/recover rather than being inferred from an address.

The native registration screen verifies phone/Google through the existing project-checked Identity Platform client. Legacy registration API rejects requests whenever owned Auth is selected. A native denial never invokes Source Auth, creates an Auth stub, or falls back. Demo-banner inline signup remains blocked in owned mode and should direct people out of demo to the normal registration page (demo module outside this slice).

Canonical initial schema and current importer preserve profiles.id -> auth.users.id CASCADE. Actual read-only candidate FK metadata was independently confirmed by the orchestrator; app_accounts has no inverse profiles FK. Proposed SQL in `docs/proposals/native-registration-owned-only.sql` drops only this legacy profile FK and permits native-registration provenance. It asserts the exact FK and seven-account baseline, locks affected tables and checks full-row hashes before commit. Existing IDs/roles/memberships/account-disabled state remain unchanged. It is deliberately outside automatic migration paths and HAS NOT BEEN APPLIED. Registration must stay disabled until the exact SQL is reviewed/applied to the OWNED candidate. Other three Auth FKs (customer_profiles,orders,waiter_calls) remain a separate blocker for those fresh-user features and are untouched here. Never apply this SQL to Source Supabase.

Native onboarding uses the server session UUID and shared admin pool (max2), locks the current profile/account, rejects disabled/recovery/superadmin/preview/demo contexts, and calls the existing complete_onboarding function on own PostgreSQL. Canonical entry-plan, role promotion and idempotent catalog repair semantics remain. No client account/tenant/role input is accepted. Existing UI access reads use the native endpoint and cannot fall back to Source. CRM enqueue is intentionally absent from the owned branch because its current worker reads Source SQL; CRM needs its own native adapter before owned restaurants can sync.

CI runs unit boundary tests, disposable PostgreSQL creation/conflict/rollback/schema-preservation tests, TypeScript/build and existing E2E. External SMS/Google and real production onboarding have not been exercised; flags remain false. The disposable suite alone runs the proposed SQL on a synthetic database named xmartmenu, never .env or live data.
